LLVM Pass Analysis: LingoDB (/home/pei/Project/lingo-db) vs AQP Middleware
==============================================

Scope
-----
This analysis covers ONLY the JIT compilation paths in ir_to_llvm.cpp:
  - expr-jit:     CompileExpr, CompileFilter
  - operator-jit: CompileProjection, CompileAggUpdateDirect,
                   CompileFilterAggFusion, CompileFilterProbeProjectFusion
  - pipeline-jit:  CompilePipeline (fused filter+projection)

All 9 call sites of OptimiseModule() are in these Compile* functions.

NOT in scope: ExecutePipelineKernel (src/kernel/pipeline_kernel.cpp).
The kernel is pure C++ compiled at build time, optimised by GCC/Clang,
with hand-coded AVX2 hashing and adaptive probe methods.  LLVM passes
have zero effect on the kernel path.

When running with --kernel-path=pipeline, the kernel handles sub-query
execution but DuckDB operators still use JIT-compiled functions.  So
the pass pipeline still matters for --jit-level=operator workloads.

Context
-------
Both projects JIT-compile query operators to native code via LLVM ORC JIT.
The generated LLVM IR is structurally simple: flat loops over column arrays
with pointer arithmetic, conditionals, and hash computation.

Main compilation paths (CompileFilter, CompilePipeline, CompileFilterAggFusion,
CompileFilterProbeProjectFusion) use PHI nodes for loop variables -- no
scalar allocas for SROA to promote.

CompileRangeFilter (ir_to_llvm.cpp:4821-4953) uses scalar allocas but is
DEAD CODE: zero call sites in the entire codebase (verified 2026-06-05).
It was added in commit 45638c3 as infrastructure for range predicate
injection, but the approach was abandoned in favour of SQL-level injection.
Safe to delete.

The batch_probe_ path in CompileFilterProbeProjectFusion (line 6310-6312)
emits 2048-element array allocas (hash_arr, htoff_arr, filt_mask).  These
are too large for SROA/mem2reg to promote.  See "Batch-Probe Array Allocas"
section below for details.

No auto-vectorisable loop nests.  Runtime function calls (memcmp, aqp_str_eq,
aqp_ht_probe, etc.) are registered as external JIT symbols -- inliner cannot
inline them.

LLVM version: 14 (primary), 19 (fallback).  All proposed passes and APIs
work on LLVM 14+.  No LLVM 20 required.

  static llvm::Error performDefaultLLVMPasses(llvm::Module* module) {
      llvm::legacy::FunctionPassManager funcPM(module);
      funcPM.add(llvm::createInstructionCombiningPass());
      funcPM.add(llvm::createReassociatePass());
      funcPM.add(llvm::createGVNPass());
      funcPM.add(llvm::createCFGSimplificationPass());
      funcPM.doInitialization();
      for (auto& func : *module) {
          if (!func.hasOptNone()) funcPM.run(func);
      }
      funcPM.doFinalization();
      return llvm::Error::success();
  }

Batch-Probe Array Allocas (CompileFilterProbeProjectFusion)
-----------------------------------------------------------
batch_probe_ defaults to true (param_config.h:97, passed via
duckdb_adapter.cpp:2318).  When enabled, 3 stack arrays are emitted:

  hash_arr_buf  = CreateAlloca(i64, 2048)   -- 16 KB
  htoff_arr_buf = CreateAlloca(i64, 2048)   -- 16 KB
  filt_mask_buf = CreateAlloca(i8,  2048)   --  2 KB

These implement a two-stage ROF (Reorder + Filter) pattern:
  Stage 1: filter all rows, compute hash + ht_offset, store to arrays
  Stage 2: read arrays, software-prefetch, hash table probe

Passes tested against representative two-stage IR (opt-14, 2026-06-05):

  SROA / mem2reg:     NO CHANGE - dynamic-sized array allocas ineligible
  LoopVectorize:      NO CHANGE - opaque calls block vectorisation
  SLPVectorize:       NO CHANGE - stores to different arrays
  DSE:                NO CHANGE - all stage-1 stores read by stage-2
  MemCpyOpt:          NO CHANGE - no memcpy patterns
  GVN:                NO CHANGE - no redundant loads (each at unique index)
  LICM:               MINOR     - hoists nrows_m1 to preheader only
  InstCombine:        MINOR     - canonicalises alloca form, no perf impact
  SimplifyCFG (O1):   YES       - merges s1_fail into s1_next (saves 1
                                  store + 1 block per iteration)
  LoopRotate (O1):    YES       - converts s1_outer while->do-while
  ADCE (O1):          YES       - removes dead out_count computation

Conclusion: the 4-pass pipeline (InstCombine, Reassociate, GVN, SimplifyCFG)
captures the SimplifyCFG benefit on the batch_probe_ path.  LoopRotate and
ADCE provide marginal additional benefit but are not critical.

No LLVM pass can vectorise the two-stage pattern.  Any vectorisation of
hash computation or mask stores would require manual SIMD intrinsics at
the IR generation level (already done in the kernel path via AVX2).

Recommendation
--------------
Replace buildPerModuleDefaultPipeline with a custom 4-pass pipeline matching
lingo-db.  Expected compilation time reduction: 3-5x at O1, 5-8x at O2.
Execution time should be equivalent (the 4 passes cover everything that
matters for our IR shape).

Verified with opt-14: O1 output vs 4-pass output differs only in cosmetic
attributes (nuw flags, function attributes, loop form).  Core IR is identical.

Implementation (new-pass-manager API, works on LLVM 14+):

  static void OptimiseModule(Module &mod, OptLevel opt) {
    if (opt == OptLevel::O0) return;

    PassBuilder pb;
    LoopAnalysisManager lam;
    FunctionAnalysisManager fam;
    CGSCCAnalysisManager cgam;
    ModuleAnalysisManager mam;
    pb.registerModuleAnalyses(mam);
    pb.registerCGSCCAnalyses(cgam);
    pb.registerFunctionAnalyses(fam);
    pb.registerLoopAnalyses(lam);
    pb.crossRegisterProxies(lam, fam, cgam, mam);

    FunctionPassManager fpm;
    fpm.addPass(InstCombinePass());
    fpm.addPass(ReassociatePass());
    fpm.addPass(GVNPass());
    fpm.addPass(SimplifyCFGPass());

    ModulePassManager mpm;
    mpm.addPass(createModuleToFunctionPassAdaptor(std::move(fpm)));
    mpm.run(mod, mam);
  }
